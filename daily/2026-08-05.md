### 2. 完成 PR #17 技术审计并推动阻塞项修复

Neo 对 PR #17 `feat/canonical-requirements-hash` 进行了技术审计，确认并提交 Request Changes：

- 可选 `walletConsistency` 被写成自有 `undefined` 属性，导致两参数 `buildE3()` 抛错。
- `Date`、`Map`、`Set` 等非 plain object 会被静默 canonicalize 为 `{}`，形成哈希碰撞路径。
- E1 仍使用非法占位哈希，未与真实 `POTATO_REQUIREMENTS_HASH` 对齐。
- 新增哈希边界缺少最小可运行回归测试。

原作者随后在原分支修复上述问题并补充 Node 原生测试。GitHub 当前状态显示 PR #17 已于今日合并。

### 3. 收敛 E3 类型统一与 PR 关系

- PR #18 最初基于 #17，负责真实 Moss E3 证据；团队确认 `moss-bridge` 的 `E3Evidence` 与 domain 的 `MossPreSignEvidence` 已发生类型漂移。
- 类型统一不塞入 #17，也不留到 E3 合并之后；应在 E3 PR 内删除重复手写类型、复用 domain 类型，并让 `buildE3()` 直接生成最终存档形状后再计算 hash。
- GitHub 当前状态显示 #18 已关闭，接续工作整理为 PR #19，base 为 `main`。

### 4. 完成 PR #19 E3 真实性审计

Neo 已在 PR #19 提交审计评论并 Request Changes。当前确认的合并阻塞包括：

1. 归档的 `capabilityParams` 由调用方提供，未绑定真实传给 Moss 的参数；`requirementsHash` 还存在十进制实参和十六进制归档值不一致。
2. 真实模拟使用 8 月 5 日的 deadline，但案件、E3 外层时间和业务时间线仍停留在 8 月 1 日，不能证明是同一笔任务的签前证据。
3. `rpcFingerprint` 未从实际 Runtime 派生，且保存完整 RPC URL 可能泄露私密 token 或凭据。
4. 干净 clone 下根目录 `pnpm test` / `pnpm typecheck` 仍受 Moss file-link、dist 和 lockfile 链路影响，PR 声明的完整门禁暂不可复现。
5. `validateCase()` 未捕获 malformed E3 的 canonicalization 异常；嵌套 `Date` 等非法值会直接抛错，而不是返回结构化 P0 issue。

截至本次打卡，PR #19 仍为 Open，尚未合并，等待作者修复后重新审计。

### 5. 更新 C4 不可判定时的资金规则

团队把 C4 无法判断时的规则从“支付 0.15 MON、冻结 0.05 MON”调整为“0.2 MON 全额冻结”。判断依据是：交付物整体不可用时，格式合规不具备可独立结算的 75% 价值。

- Eleven 前端读取数据字段，规则数据更新后应自动显示 0.2 MON，无需单独改展示逻辑。
- Neo 的合约 `settle` 已支持传入全额 `frozen`，本次规则调整无需修改合约。
- 该规则仍需随后续代码上传和浏览器 / 测试证据一起复核，本次只记录团队决策，不把未验证代码写成已完成。

## 遇到的问题

- **问题 1：PR 依赖关系容易产生并行主线**
  - **原因**：#18 依赖 #17，同时 #17 又需要修复。
  - **处理**：让原作者直接更新 #17；#17 合并后再让 E3 工作回到 `main`，不额外创建并行修复 PR。
- **问题 2：哈希正确不等于证据真实**
  - **原因**：调用方可传入与 Moss 实际输入、Runtime 或案件时间线不一致的归档字段。
  - **处理**：要求从 `PreparedTask` / Runtime 边界携带真实且去敏的数据，再由 `buildE3()` 构造最终存档对象。
- **问题 3：完整门禁无法在干净环境复现**
  - **原因**：Moss file-link、dist、Node 类型与 lockfile 链路存在基础设施问题。
  - **处理**：先修复依赖链并 rebase #19，再重跑根目录测试、typecheck 和 ABI gate；未通过前不合并。
