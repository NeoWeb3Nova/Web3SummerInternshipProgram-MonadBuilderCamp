## 待验证的问题（复述）

**问题句：**当使用 Agent 钱包的个人用户准备执行一笔链上交易时，是否会因为看不懂 Agent 的交易提案与模拟结果而盲目确认，并在结果异常后因缺少「用户意图—Agent 提案—风险提示—用户确认—实际执行」的连续记录而难以还原事实？

**本轮预演目的：**用 3 个差异明显的 AI Persona 对问题进行压力测试，提前发现访谈盲区和产品范围风险。以下内容是基于 Persona 设定生成的假设，不代表真实用户证据。

---

## 正式访谈问题清单

1. 你最近一次遇到这个问题是什么时候？
2. 当时你是怎么解决的？
3. 哪一步最麻烦、最担心或最浪费时间？
4. 现有办法为什么不够好？
5. 如果只能改进一件事，你最希望是什么？
6. 你是否愿意体验我们的第一版？

## AI Persona 模拟记录（3 人）

### Persona 1｜刚开始使用 DeFi 的 Agent 钱包新手

| 字段 | 内容 |
|------|------|
| **用户类型** | 有钱包、做过少量 Swap，但看不懂 calldata、授权额度和复杂路由的个人用户。 |
| **是否遇到过类似问题** | Persona 假设：遇到过。Agent 给出交易后仍需要面对钱包弹窗，不知道它是否真的只执行了自己说的那件事。 |
| **最近一次经历** | 让 Agent 帮忙把 USDC 换成 MON，看到 approve 和 swap 两次确认，不知道为什么要授权，也不知道授权额度是否过大。 |
| **现有解法** | 先用很小金额尝试；在区块浏览器查看结果；不确定时直接取消，并向群友询问。 |
| **最在意什么** | 钱会不会转错、授权是否会长期有效，以及最终收到的数量是否与页面承诺一致。 |
| **最希望改进的一件事** | 签名前只用一屏说明「我将付出什么、得到什么、授权给谁、最坏会损失什么」。 |
| **是否愿意试用第一版** | 有条件：不托管私钥、不自动签名，而且解释必须比钱包原始弹窗更简单。 |
| **模拟原话** | 「我不想看一份审计报告，我只想知道最坏会损失多少。」 |

### Persona 2｜有 DeFi 经验的高频用户

| 字段 | 内容 |
|------|------|
| **用户类型** | 经常使用 DEX、借贷协议和钱包模拟功能，能阅读基本的资产变化与授权信息。 |
| **是否遇到过类似问题** | Persona 假设：部分遇到。签名前解释不是最大痛点，更担心模拟的交易与最终签名、广播的交易是否完全一致。 |
| **最近一次经历** | 聚合器报价在等待签名期间发生变化，最终执行价格与预期不同；事后只能手工对照报价截图、钱包活动和链上事件。 |
| **现有解法** | 使用钱包自带模拟、区块浏览器和协议页面交叉检查；高风险交易会保存截图，或先用模拟工具验证。 |
| **最在意什么** | Agent 提案、模拟输入、用户签名和最终广播交易之间是否绑定；记录能否证明中间没有被替换。 |
| **最希望改进的一件事** | 给每次确认生成可验证的摘要，明确关联原始意图、模拟结果、待签名交易哈希与最终交易哈希。 |
| **是否愿意试用第一版** | 是，但要求默认保护策略、金额和地址等隐私，不能把完整对话永久公开上链。 |
| **模拟原话** | 「解释可以生成，但最关键的是：我签的必须就是刚才模拟的那一笔。」 |

### Persona 3｜钱包安全 / 智能合约开发者

| 字段 | 内容 |
|------|------|
| **用户类型** | 熟悉合约调用、交易模拟和钱包安全边界的开发者，也可能负责审查 Agent 交易流程。 |
| **是否遇到过类似问题** | Persona 假设：遇到的是审计问题，而不是「看不懂」。系统通常能保存交易，但无法证明用户当时看到了哪项风险提示，以及提示对应哪个确定版本的交易。 |
| **最近一次经历** | 调试一条多步交易时，模拟结果来自旧参数，随后前端更新了交易；日志存在，但缺少统一版本标识，无法快速判断错在 Agent、UI 还是广播环节。 |
| **现有解法** | 保存结构化日志、请求 ID、模拟输入输出和交易哈希；发生异常时人工拼接服务端日志与链上数据。 |
| **最在意什么** | 数据规范化、哈希可复现、模拟可信度、版本绑定和证据来源；不希望产品宣称仅凭日志就能判定法律责任。 |
| **最希望改进的一件事** | 定义最小「决策收据」标准，并允许第三方独立验证收据内容与链上锚点是否一致。 |
| **是否愿意试用第一版** | 是，前提是展示原始结构化证据，且明确 Moss 模拟、UI 解释和链上执行各自的信任边界。 |
| **模拟原话** | 「链上哈希只能证明某份数据曾经存在，不能证明用户真的理解了它。」 |

## 交叉结论

| 类型 | 内容 |
|------|------|
| **三人模拟共性** | 都需要确认 Agent 提案、模拟结果、待签名交易与最终执行之间没有发生未告知的变化；都反对托管私钥或自动签名。 |
| **用户层级差异** | 新手优先需要简洁的损失与授权说明；高频用户更在意交易绑定和隐私；开发者更在意证据格式、来源与可复现性。 |
| **可能只是 Persona 假设** | 个人用户是否真的会在事后主动查看决策收据，以及是否愿意为收据上链支付成本，必须由真人访谈验证。 |
| **最意外的一条模拟反馈** | 「留下证据」不等于「用户已经理解风险」。产品不能把用户点击确认包装成免责证明，应只记录事实，不自动判责。 |
| **新问题** | 如何证明用户看到的解释与他最终签署的交易属于同一个不可替换版本，同时不把完整意图、策略和资产信息公开上链？ |

---

## 模拟反馈摘要

### 他们现在怎么解决？

- 新手用小金额试错、取消交易或询问群友。
- 高频用户结合钱包模拟、协议页面、截图和区块浏览器人工核对。
- 开发者保存结构化日志、请求 ID 和交易哈希，异常时再人工拼接。

### 他们最在意什么？

1. 最终签署的交易必须与刚刚解释、模拟的交易一致。
2. 签名前需要看到金额、授权对象、最坏损失和关键 Warning。
3. 决策记录必须保护隐私，并且只记录事实、不宣称自动判责。

### 最意外的反馈是什么？

最意外的不是用户要求「记录更多」，而是他们提醒：**证据越完整，也越不能假装用户已经理解。** 因此，产品价值应从「责任归属系统」收缩为「交易版本绑定 + 可核验决策收据」。

**初步原因：**模拟结果支持「交易解释与执行之间缺少可靠绑定」这一问题，但不足以证明个人用户需要完整的责任时间线。第一版先聚焦一笔 Swap 的签前解释、交易版本绑定和本地决策收据。

**对 Demo 的影响：**

- **保留：**Moss `action → simulate`、结构化资产变化与 Warning、用户明确确认、待签名交易哈希、最终交易哈希、收据完整性校验。
- **缩小：**只支持一笔 Swap；只生成一份最小决策收据；链上只锚定收据哈希。
- **砍掉：**自动判责、法律责任评分、完整聊天记录上链、多协议、多角色审批和自动执行。
- **正式开发前必须验证：**找 3 位真人确认他们最近是否遇到过类似问题、现在如何解决、是否愿意查看或保存决策收据。
