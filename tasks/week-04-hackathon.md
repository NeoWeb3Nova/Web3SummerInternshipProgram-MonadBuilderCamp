# Week 4｜Monad Playground Hackathon

> 第四周正式进入 **Monad Playground Hackathon**。  
> 这一周**不要求立刻完成完整产品**，重点是：认识 Builder、分享 Idea、寻找队友、判断需求，并确定下一周最先完成什么。

---

## 本周定位

你可以：

- 继续 Week 3 的团队和项目
- 更换方向、加入其他团队
- 从一个新的 Idea 开始

暂时没有 Idea、不会写代码、还没有队友，**也可以参加**。

黑客松团队不只需要开发者，也需要研究、产品、设计、运营和表达。

### 两周节奏（先记住）

| 阶段 | 重点 |
|------|------|
| **本周（Playground）** | 发出协作信号 → 找到真实问题 → 组队 → 用 3 人验证需求 → 写清下一周第一步 |
| **下一周（Build Sprint）** | 围绕一个核心体验冲刺可演示 Demo（本周先定范围，不急着堆功能） |

---

## 本周原则

- 先让别人知道你是谁，再谈写代码
- 从真实困惑出发，不硬想功能
- 组队可试合作、可调整、可合并
- 先问三个人，再决定做什么
- 第一版只做**一个可被体验、被解释、被检查**的核心动作
- 记录真实反馈与决策，作为后续 Build Sprint 的依据

## DAY 1｜Enter the Playground：先让别人知道你是谁

### 🎯 学习目标

- 理解 Monad Playground 的参与方式与两周节奏
- 知道黑客松团队不只有开发者，也需要研究、产品、设计、运营和表达
- 用简短信息说明自己的兴趣、能力、时间和协作需求
- 发现自己更适合「带 Idea 找队友」还是「带能力找项目」

### 📖 学习内容

黑客松的第一步不是写代码，而是发出清楚的**协作信号**。

一条好的 Builder Signal 应让别人快速知道：

1. 你对什么问题或方向感兴趣？
2. 你可以提供什么能力？
3. 你希望学习或尝试什么？
4. 你每周大约可以投入多少时间？
5. 你希望寻找什么样的项目或队友？

**不要只写「求组队」或「什么都可以」。**  
即使你是新人，也可以贡献：产品体验、资料整理、用户访谈、视觉设计、活动传播、测试、视频或 Pitch 等。

### 💬 Co-Learning

参加当晚 20:00 Co-Learning，完成 **60 秒 Builder Intro**。  
可以直接分享不成熟的兴趣，不需要提前准备完整项目。

### 🛠 今日任务｜Builder Signal +10

在群内或 Co-Learning 中发布一张 Builder Signal，并写入仓库：

| 字段 | 填写提示 |
|------|----------|
| 我的方向或兴趣 | 问题域 / 赛道 / 用户场景 |
| 我能贡献 | 具体可检查的能力或动作 |
| 我想学习 | 本周/下周期望练到的技能 |
| 我每周可投入时间 | 小时数或可用时段 |
| 我有 Idea / 想加入团队 | 二选一或两者都有 |
| 我希望寻找的队友或项目 | 角色互补、问题类型、协作方式 |

## DAY 2｜Find a Real Problem：从真实困惑出发，而不是硬想功能

### 🎯 学习目标

- 学会从真实体验、社群问题和重复流程中寻找 Idea
- 区分「技术概念」「功能想法」和「用户问题」
- 用一句话讲清目标用户、具体场景和问题
- 学会评价一个 Idea，而不是只说「很好」或「没意思」

### 📖 学习内容

适合新人黑客松的 Idea **不需要宏大，但应该足够具体**。

推荐从这些地方寻找：

- 自己第一次使用钱包、DApp、Gas、跨链或签名时遇到的困难
- 社群里反复被问到的问题
- Monad 生态中难以发现、理解或使用的产品
- 需要不断复制、整理、查询或人工确认的流程
- Week 3 测试中没有解决好的用户问题
- Moss 可以帮助用户准备、模拟或解释的链上操作

**问题句模板：**

> 当【某类用户】在【具体场景】想完成【目标】时，会因为【障碍】而遇到困难，目前只能通过【现有方式】解决。

区分三层表述：

| 类型 | 示例 | 是否够具体 |
|------|------|------------|
| 技术概念 | 「做一个 AI Agent」 | 否，还不是用户问题 |
| 功能想法 | 「加一个交易模拟按钮」 | 偏方案，缺场景 |
| 用户问题 | 「小白在确认 swap 前看不懂授权与滑点风险」 | 是 |

### 💬 Co-Learning

轻量 **Idea Market**：

1. 每人用 **1 分钟** 分享一个问题或 Idea
2. 其他人只能提问、补充案例或提供证据，**先不急着否定**
3. 对感兴趣的 Idea 留下：「我想加入」「我可以提供……」或「我遇到过同样问题」

### 🛠 今日任务｜Problem & Idea Card +20

提交一张值得验证的 Idea（可以不成熟，但要具体）：

| 字段 | 内容 |
|------|------|
| 问题句 | 用上面的一句话模板 |
| 目标用户 | 谁会反复遇到 |
| 场景与障碍 | 什么时候、卡在哪一步 |
| 现有替代方式 | 现在人们怎么凑合 |
| 为什么值得验证 | 证据：亲身经历 / 社群重复 / Week 3 反馈 等 |
| 我能提供的切入 | 研究 / 产品 / 设计 / 开发 / 运营 / Pitch… |
| 可选：Moss / Monad 关联 | Agent 能准备/模拟/解释什么？为何适合 Monad？ |

## DAY 3｜Meet Your Team：找到愿意一起行动的人

### 🎯 学习目标

- 判断队友是否在时间、目标和工作方式上匹配
- 学会用**具体贡献**加入团队，而不是等待别人分配
- 允许团队调整、合并或重新组队
- 建立最小协作方式，不花大量时间制定复杂规则

### 📖 学习内容

组队不等于一次决定后永远不能改变。Hackathon 第一周允许自由交流和试合作。

找到潜在队友后，先确认四件事：

1. 我们是否对**同一个用户问题**感兴趣？
2. 每个人能投入多少时间？
3. 每个人准备完成什么**可检查的贡献**？
4. 如果方向不成立，我们是否愿意一起调整？

补充约定：

- 可以先试合作一天，再决定是否正式组队
- 没有开发者的团队可以先做需求、原型和招募
- 没有 Idea 的开发者也可以带着能力加入现有项目
- 相似 Idea 的团队可以考虑合并

### 💬 Co-Learning

**Team Matching**：

1. Idea Holder：60 秒介绍问题与需要的角色
2. Builder：30 秒介绍自己可以贡献什么
3. 落单同学：说明「我想加入哪类项目」
4. 助教帮助角色互补的同学建立联系，也帮助相似 Idea 考虑合并

### 🛠 今日任务｜Team Matching Card +20

| 字段 | 内容 |
|------|------|
| 组队状态 | 已组队 / 试合作 / 寻找中 / 加入他人项目 |
| 团队成员与角色 | 姓名/代号 + 主责 |
| 共同关注的用户问题 | 一句话对齐 |
| 每人可投入时间 | 小时数或可用时段 |
| 每人可检查贡献 | 本周能交付什么证据 |
| 若不成立如何调整 | 缩小 / 换方向 / 合并 / 拆队 |
| 最小协作方式 | 群、同步时间、文档位置 |

## DAY 4｜Test Before Build：先问三个人，再决定做什么

### 🎯 学习目标

- 用低成本方式判断问题是否真实
- 避免只让 AI 或队友证明自己的想法
- 了解用户现在的解决方式和真正关心的部分
- 根据反馈保留、调整、合并或放弃 Idea

### 📖 学习内容

需求验证不需要写正式研究报告。你只需要找到 **3 位可能遇到这个问题的人**，进行简短交流或任务观察。

**不要只问**：「你觉得这个 Idea 好不好？」

可以问：

1. 你最近一次遇到这个问题是什么时候？
2. 当时你是怎么解决的？
3. 哪一步最麻烦、最担心或最浪费时间？
4. 现有办法为什么不够好？
5. 如果只能改进一件事，你最希望是什么？
6. 你是否愿意体验我们的第一版？

如果三个人都没有经历过这个问题，**不代表任务失败**——这可能在帮助团队及时换方向，避免下一周做出没人需要的 Demo。

决策标签（团队自选其一）：

| 结论 | 含义 |
|------|------|
| **继续** | 问题真实，范围基本成立 |
| **缩小** | 问题存在，但先砍到更小场景 |
| **调整** | 用户不同 / 障碍不同 / 场景不同 |
| **合并** | 与相邻 Idea 合并更有力 |
| **暂停** | 证据不足或优先级不够，本轮不做 |

### 💬 Co-Learning

**Idea Reality Check**：

1. 团队分享最重要的一条真实反馈
2. 大家帮助判断：继续 / 缩小 / 调整 / 合并 / 暂停
3. 可将用户或测试者提出的新问题放回 Idea Pool，供其他团队探索

### 🛠 今日任务｜3-Person Reality Check +20

对 3 位访谈对象各记一条摘要，并给出团队结论：

| 字段 | 内容 |
|------|------|
| 访谈对象 1–3 | 谁、为何相关（可匿名） |
| 关键原话 / 观察 | 最近一次经历、现有解法、最痛一步 |
| 交叉结论 | 共性问题 vs 个例 |
| 团队决定 | 继续 / 缩小 / 调整 / 合并 / 暂停 |
| 对 Demo 的影响 | 下周验证什么、砍掉什么 |

## DAY 5｜Choose Your First Move：确定下一周先做什么

### 🎯 学习目标

- 把 Idea 缩小为两周内能够展示的核心体验
- 明确团队下周的**第一步**，而不是制作庞大 Roadmap
- 区分：真实实现 / 可用现成工具 / 可以 Mock 的部分
- 判断团队是否准备进入 Build Sprint

### 📖 学习内容

第一版 Demo 只需要让用户完成**一个核心动作**。

团队需要回答：

1. 用户是谁？
2. 用户要完成什么动作？
3. 完成后得到什么价值？
4. 哪一部分必须真实运行？
5. 哪一部分可以先用 Figma、Mock 数据、现成组件或人工流程？
6. 为什么适合 Monad？
7. 如果选择 Moss：Agent 准备、模拟或解释了什么链上操作？
8. 下一周最先验证的**风险**是什么？

**不要把第二周排满功能。** 先选择一个可以被体验、被解释、被检查的版本。

### 💬 Co-Learning

**90 秒 Project Check-in**：

| 时段 | 内容 |
|------|------|
| 30 秒 | 用户与问题 |
| 30 秒 | Demo 的一个核心动作 |
| 30 秒 | 团队、当前阻塞与需要的帮助 |

听众提供一条具体建议或一个可用资源。  
团队**不需要正式 Pitch**，也**不做排名**。

### 🛠 今日任务｜Hackathon Start Card +30

| 字段 | 内容 |
|------|------|
| 项目名（可暂定） | |
| 用户与问题 | 一句话 |
| Demo 核心动作 | 用户只完成这一件事 |
| 完成后的价值 | 用户得到什么 |
| 必须真实运行 | 列表 |
| 可 Mock / 现成工具 | 列表 |
| 为什么适合 Monad | 一句可辩护的理由 |
| Moss（若使用） | 准备 / 模拟 / 解释了什么 |
| 下周最先验证的风险 | 技术 / 需求 / 协作 中的头号风险 |
| 团队与角色 | |
| 需要的帮助 | 招募 / 资源 / 导师问题 |
| 是否进入 Build Sprint | 是 / 条件就绪后 / 暂缓 |
